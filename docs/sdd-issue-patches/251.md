## Contrato de tests (obligatorio en el PR)

Archivo sugerido: `tests/unit/test_question_queue.py` (+ CLI dry-run; sin red; sin Cloud API real).

1. **Dedup id:** la misma pregunta desde `jobs conditions` dos veces → **un** `Question` (mismo id); si el prompt cambia y status es `pending`, se actualiza el texto.
2. **Orígenes:** conditions `ask`, answers en blanco, portal screening (`form_learn`), manual → encolan con `origin.kind` distinto y `destination` / `target_file` correctos.
3. **Send dry-run:** comando de envío sin `--apply` imprime el mensaje numerado (deeplink) y **no** marca `sent` ni llama a la API.
4. **Send HITL:** con `--apply` + confirm → status `sent` + evento en history; sin confirm → no cambia.
5. **Ingest:** texto pegado «1) B2» mapea al id #1; respuesta no inventa campos fuera del destino.
6. **Apply HITL:** aplicar a `application_answers.yaml` / profile muestra diff y requiere confirm; default N; nunca escribe sin sí.
7. **Prohibiciones:** no envía passwords/OTP/documentos; no hay cron auto-send; suite offline (deeplink URL construida, API mockeada).

## Justificación

Las preguntas HITL están dispersas (conditions, answers, formularios); WhatsApp es el canal de la candidata, no el SoT. Una cola con id estable + apply con diff evita inventar hechos y evita Playwright no oficial. El digest de avisos (`jobs digest --format whatsapp`) ya prueba el formato; este issue es la cola de **preguntas**, no el resumen de jobs.
