## SDD / patrones

- **SDD:** `docs/software-design.md` §2 presentation (`cli`) · local single-writer safety (mismo espíritu que owner stamp / profile_busy)
- **Patrón(es):** **Mutex** / exclusive lock file (pid + stale reclaim); Command `update_jobbot` toma el lock antes de `uv tool install --force` y lo suelta en `finally`
- **UML:** [`docs/uml.md#update-mutex`](../uml.md#update-mutex) · [`plan-apply`](../uml.md#plan-apply)
- **Cambio de diagrama:** el PR tipa `UpdateLock` (path, pid) y actualiza `update-mutex`

## Contrato de tests (obligatorio en el PR)

Archivo sugerido: `tests/unit/test_update_lock.py` (sin llamar a `uv` real; mock del instalador).

1. **Lock vivo:** con un archivo de lock cuyo pid **existe**, `update_jobbot` **no** invoca `uv tool install` y sale 1 con mensaje de que ya hay una actualización.
2. **Lock stale:** lock con pid que **no** existe → se reclama el lock y la reinstalación (mock) sigue.
3. **Liberación:** tras éxito o fallo de la instalación mock, el lock **no** queda en disco (o queda marcado liberado de forma comprobable).
4. **Ubicación:** el lock vive junto al perfil / data local del workspace (no en el checkout compartido de varios candidatos sin workspace).

## Justificación

Dos `jobbot update` / `-U` concurrentes pueden pisar el ejecutable a mitad de `uv tool install --force`. Un lock con reclaim de pid muerto es el contrato mínimo de proceso único sin depender de un servicio externo.
